# 视桥边缘推理与 WebRTC 低延迟优化记录

日期：2026-08-03

## 结论

识别模型一直运行在树莓派本机，图片没有上传到第三方平台后再推理。原问题不是“没有边缘化”，而是树莓派 4 的 32 位 ARM CPU 推理、固定 320 输入模型、额外推理等待、重复 JPEG 编解码及软件 H.264 编码共同争抢算力。

优化后，边缘端直接把带识别框的原始 BGR 帧交给树莓派硬件 H.264 编码器，经自有云 MediaMTX/Coturn 以 WebRTC 播放。遥测与视频均不经过研华或其他第三方数据平台。

## 根因

1. 树莓派为 Raspberry Pi 4 Model B，系统是 32 位 `armv7l`。当前 ONNX 模型由 OpenCV DNN 在 CPU 上执行，没有 NPU/GPU 推理后端。
2. 原模型固定输入为 `320×320`，单帧推理约 1.2 秒。
3. 原配置在每次推理完成后再等待 1.5 秒，识别结果约 2.7 秒更新一次。
4. 原视频固定为 8 FPS，并使用 `libx264` 软件编码，FFmpeg 长期占用约 85% CPU。
5. 原媒体链路为 `BGR → JPEG → HTTP MJPEG → JPEG 解码 → H.264`，同一帧发生无意义的 JPEG 编解码。
6. Raspberry Pi 旧版 V4L2 编码器不回传 PTS；若直接复用默认时间基，媒体服务器会把 15 FPS 误判为 30 FPS，可能产生累计缓冲。

## 已实施优化

- 将固定 320 YOLOv8 ONNX 的输入、DFL reshape、anchor grid 和 stride table 一起转换为固定 `256×256`，不是只修改输入维度。
- 在 4 张历史障碍物照片上对比 320/256 模型，最高置信类别保持一致，主要置信度差异约 0.001–0.042。
- 启用连续最新帧推理，修复原先未生效的 `INFER_EVERY_N_FRAMES`，去掉完成后的额外 1.5 秒等待。
- 新增独立 `inference_fps`、`inference_period_ms` 指标，云端页面将摄像头 FPS 和模型识别 FPS 分开显示。
- 新增 `/stream.raw` 原始 BGR 帧流；15 FPS 云视频不再经过 JPEG 编解码。
- 浏览器用的 `/stream.mjpg` 保留，但降为 5 FPS JPEG 生成，避免无人观看时浪费 CPU。
- 使用 `bcm2835-codec` 的 `h264_v4l2m2m` 硬件编码器，600 kbit/s、320×240、目标 15 FPS。
- 对旧 V4L2 无 PTS 输出增加 Annex-B 二次无损 remux，以墙钟重建单调 RTSP 时间戳，避免 30/15 FPS 时间基漂移。
- HLS 反向代理补充重定向前缀修正，兼容模式的播放清单现可正常访问。
- WebRTC 仍为默认模式，HLS 只作为兼容回退。

## 实机结果

| 指标 | 优化前 | 优化后实测 |
|---|---:|---:|
| 摄像头采集 | 约 8.7 FPS（界面旧值） | 中位 14.3 FPS，范围 13.5–15.0 |
| 单帧推理 | 约 1228 ms | 中位 396 ms，范围 389–471 ms |
| 识别更新频率 | 约 0.37 FPS | 中位 2.46 FPS |
| 云视频 | 8 FPS | WebRTC 实收 14.98 FPS |
| WebRTC 媒体时间轴 | 未验证 | 14.97 FPS |
| WebRTC 首帧 | 较慢 | 775 ms |
| 8 秒测试丢包 | 未验证 | 0 |
| 视频分辨率 | 320×240 | 320×240 |
| FFmpeg CPU | 约 85% | 两个进程合计约 7%（采样值） |

公网 WHEP 返回 201，PeerConnection 状态为 `connected`。MediaMTX、Coturn、Nginx、云端 API、边缘推理、媒体隧道和媒体发布服务均处于 active 状态。

- `pi-runtime/blind_occupancy_edge_iotsuite.py`：连续推理、独立识别 FPS、原始帧流。

- `pi-runtime/tools/resize_fixed_yolov8_onnx.py`：固定 YOLOv8 ONNX 输入尺寸安全转换工具。
- `pi-runtime/models/best_256.onnx`：当前树莓派部署模型。
- `apps/dashboard/app/device-fleet.tsx`：独立展示采集帧率、推理耗时和识别频率。

## 硬件上限与后续升级

当前约 2.5 次识别/秒是 Raspberry Pi 4、32 位系统、纯 CPU OpenCV DNN 下的合理结果；视频本身已稳定接近 15 FPS，识别框在两次推理之间保持显示。若必须让模型本身达到 5–15 FPS，需要进一步采用以下至少一项：

1. 迁移到 64 位 Raspberry Pi OS，并将模型转换为 NCNN 或 TFLite INT8；需要用比赛数据集重新做精度回归。
2. 增加 Hailo-8L、Coral USB TPU 等推理加速器，并转换对应模型格式。
3. 更换带 NPU 的边缘计算硬件。

不建议继续缩小到 192 或盲目降低阈值来换速度，因为会明显伤害远距离小障碍物召回率。

## 回滚

部署前的边缘程序、媒体脚本和环境文件均保留了同目录 `*.bak-*` 备份。若需回滚，应同时恢复：边缘 Python、边缘环境文件、媒体发布脚本和媒体环境文件，然后依次重启：

```bash
sudo systemctl restart blind_occupancy_edge_iotsuite.service
sudo systemctl restart visionbridge-media-publisher.service
```
